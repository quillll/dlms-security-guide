对称加密与哈希：把每个算法的“输入—输出”讲清楚

为什么先学这一课：DLMS 的安全报文里，真正干活的是 AES-GCM；但 GCM 只是“一把锁”。你不会因为背下“Suite 0 用 AES-GCM-128”就会排错——你必须知道锁的钥匙多长、门牌（IV）怎么拼、哪些内容不加密但要防篡改（AAD）、标签（tag）几位。这一课把每个算法拆成“给它什么、它还你什么、DLMS 拿它做什么”。
先立一个坐标系：三类算法，三种完全不同的工作

对称算法（AES）：同一把钥匙锁门和开门，快，负责“保密 + 完整性”。哈希（SHA-256）：没有钥匙的“指纹”，负责“摘要”，本身不保密也不认证。非对称算法（ECDH / ECDSA）：一把公钥、一把私钥，慢，负责“协商钥匙”和“签名”。
DLMS 的 Suite 0 只有第一类；Suite 1/2 三类都有。下一课专讲第三类。

2AES：一把锁，锁 16 字节一块

2.1 它到底是什么

AES（Advanced Encryption Standard，FIPS 197）是一个分组密码：它一次只处理固定长度的数据块——128 bit = 16 字节；钥匙长度可以是 128、192 或 256 bit。DLMS 只用两种：

DLMS 里 AES 的两种强度（绿皮书 §9.2.3.3.3、§9.2.3.3.7.4）
用途Suite 0Suite 1Suite 2
块密钥 EK 长度128 bit / 16 B128 bit / 16 B256 bit / 32 B
认证密钥 AK 长度128 bit / 16 B128 bit / 16 B256 bit / 32 B
KEK（包装密钥）长度128 bit / 16 B128 bit / 16 B256 bit / 32 B
GCM tag 长度96 bit / 12 B96 bit / 12 B96 bit / 12 B
IV 长度96 bit / 12 B96 bit / 12 B96 bit / 12 B
注意 Suite 2 的 tag 并没有变长

很多人以为“Suite 2 更强，所以 tag 更长”。不是。绿皮书 §9.2.3.3.7.6 明确规定：Suite 0、1、2 的 tag 都是 96 bit。Suite 2 增强的是密钥长度、曲线和哈希，不是 tag。对接时若对端按 16 字节 tag 解析，报文会整体错位。

2.2 为什么不能直接用 AES 加密整条报文

直接按块加密（ECB 模式）有一个致命性质：同样的明文块 + 同样的钥匙 → 同样的密文块。电表报文里有大量重复结构（相同的 class_id、相同的 OBIS、成片的 00），攻击者不需要解密就能看出模式，甚至能整块替换。所以必须引入“模式”（mode of operation）：用 IV 让每次加密的结果不同，用反馈/计数器把块串起来。

加密一条报文时，IV 用发送方的 system title 与发送方当前的 invocation counter；接收方解密时，则用对端的 system title 和报文里带的那 4 字节 IC 重建 IV。不要用接收方自己的计数器去解密——这是“解密出来是乱码 / tag 对不上”的头号原因。

3.3 计数器：GCM 的安全生命线

GCM 的 IV 绝对不能在同一把钥匙下重复。DLMS 的做法是：

  • 每把 EK 配两个计数器：一个给加密方向，一个给解密方向（§9.2.3.3.7.3）。
  • 新钥匙建立时，两个计数器都清零。
  • 发一条：用当前值，然后 +1；到最大值（232−1）就报错，不再回绕。
  • 收一条：报文里的 IC 必须 ≥ 本地记录的“最低可接受值”；通过后把最低值改成 IC+1。这样旧报文重放会被拒。
换钥匙必须清零，不换钥匙绝不能清零

计数器清零只在“新钥匙生效”时发生。若你在同一把钥匙下把计数器重置，就会产生两次使用同一 IV——GCM 在这种情况下会泄露明文异或关系，tag 也可能被伪造。反过来，换了钥匙却沿用旧计数器，会让对端的“最低可接受值”检查失败。

4三种保护组合：A 位与 E 位

Security Control 字节的 bit4 是 A（authentication），bit5 是 E（encryption）。它们组合出三种真正会用到的模式（§9.2.7.2.4.3 Table 46）：

三种保护方式：明文、AAD、报文里带什么
模式SC 示例P（被加密）AAD报文携带能防什么

“仅加密”不是“弱一点的认证+加密”，它是另一件事

绿皮书 §9.2.3.3.7.1 明说：仅加密时 tag “simply not computed and checked”。这意味着攻击者可以在密文里翻位，接收方照样解密，只是得到一堆乱码——没有任何完整性保证。工程上除非有上层保护，否则不要用 0x20。很多实现会“顺手”算一个 tag，但 DLMS 既不携带也不校验它，算出来也不代表协议要求。

Sys-T = 4D4D4D0000BC614E    IC = 01234567

注意 ② 与 ③ 的密文完全一样：因为它们用同一把 EK、同一个 IV、同一段明文；区别只在 ③ 多算了一个 tag，并且 AAD 里放了 SC‖AK。这也说明：加密结果不包含 tag，tag 是另外附在末尾的。

为什么 ① 的 AAD 里要放整个 APDU，而 ③ 只放 SC‖AK？

因为 ① 不加密，APDU 是明文传输，GCM 必须把它纳入 AAD 才能保护它；如果 AAD 里不放 APDU，tag 就只覆盖了 SC 和 AK，攻击者可以随意改明文而 tag 仍然有效。
③ 中 APDU 已经被放进 P 加密，GCM 本身就会用 P 计算 tag，所以 AAD 只需要放“不加密但必须认证”的 SC 与 AK。

5GMAC：把 GCM 的“加密”关掉

GMAC 不是一个新算法，而是 GCM 在 P = 空 时的特例：只对 AAD 生成 tag。DLMS 用它做两件事：

  1. 仅认证的报文保护（SC 的 A=1、E=0），例如某些只要求完整性的读表响应。
  2. HLS mechanism 5 的挑战应答：T = GMAC(SC‖AK‖StoC)，输出 f(x)=SC‖IC‖T（Table 50）。

它的计算和 ① 完全同构，只是被认证的内容从 APDU 换成了挑战值。第 11 课会把 HLS 的四趟流程和 IV 取值讲透；这里先记住一句话：GMAC 仍然需要 IV，不是“没有加密就不用 IV”。

6AES Key Wrap：把一把钥匙装进信封

6.1 它解决什么问题

你要把新的 GUEK 从客户端送到服务端，但链路上可能已经有攻击者。直接发不行；用另一把钥匙加密它，又需要一个“钥匙的钥匙”——这就是 KEK（Key Encrypting Key，密钥加密密钥）。AES Key Wrap（RFC 3394）就是专门做这件事的算法：

  • 输入：KEK + 要包装的密钥（n 个 64-bit 块，n ≥ 2）。
  • 输出：n+1 个 64-bit 块，也就是比原文多 8 字节。
  • 多出来的 8 字节是完整性校验值（默认 IV = A6A6A6A6A6A6A6A6），解包时会验证；被改过就解包失败。
  • 它不是普通 AES 加密：不能拿它加密任意长度的数据，它是“密钥专用信封”。

7SHA-256 / SHA-384：没有钥匙的指纹

哈希函数把任意长度的输入压成固定长度的输出，且不可逆、难碰撞。DLMS 用它们做三件事：

  • KDF：把 ECDH 算出的共享秘密 Z 派生成密钥（§9.2.3.4.6.5）。
  • ECDSA：签名前先对消息做哈希（§9.2.3.4.4）。
  • HLS mechanism 6：SHA-256(HLS_Secret‖SysT-C‖SysT-S‖StoC‖CtoS)。
算法输出DLMS 中的位置现状
MD5128 bitHLS mechanism 3规范明确“不推荐用于新实现”
SHA-1160 bitHLS mechanism 4同上，已不适合新设计
SHA-256256 bitSuite 1 的 KDF/ECDSA；HLS mechanism 6主力
SHA-384384 bitSuite 2 的 KDF/ECDSASuite 2 主力
哈希不是“加密”，也不能当 MAC 单独用

SHA-256(报文) 谁都能算，所以它不能证明“是谁发的”。要认证必须用带密钥的结构：GMAC、HMAC，或 HLS 里那种“秘密 ‖ 挑战”的约定。DLMS 没有在报文保护里直接用裸哈希。

8KDF：从共享秘密到“能用的钥匙”

8.1 为什么不能把 Z 直接当钥匙

ECDH 算出的 Z 是一个椭圆曲线点坐标，长度、分布、用途都不一定适合直接做 AES 钥匙；而且同一对密钥可能要为“加密”“认证”“KEK”派生多把钥匙。所以要经过 KDF（Key Derivation Function）。DLMS 选的是 NIST 的 Concatenation KDF（SP 800-56A §5.8.1.1）：

K(i) = Hash( counter(i) ‖ Z ‖ OtherInfo )
counter(i) = 4 字节大端，从 1 开始
派生密钥 = K(1) ‖ K(2) ‖ … 截取到 keydatalen 位

OtherInfo = AlgorithmID ‖ PartyUInfo ‖ PartyVInfo
          = AlgID(7 B) ‖ IDU(8 B) ‖ IDV(8 B)      （C(2e,0s) / C(1e,1s)）
          = AlgID(7 B) ‖ IDU(8 B) ‖ NonceU ‖ IDV(8 B)（C(0e,2s)）

本课脚本对 C.2 的两个方向做了对照：同一套算法，KDF(Z, AlgID, Sys-TC, Sys-TS) 得到 59A71FD8…，而 KDF(Z, AlgID, Sys-TS, Sys-TC) 得到 F0184BDA…。谁是 U、谁是 V 不是“随便”，而是由报文里的 originator / recipient 角色决定。第 12 课会用时序图讲清。

9V.44 压缩：唯一一个“不是密码学”的套件成员

Suite 1 与 Suite 2 的算法表里还有 V.44 压缩。它不提供任何安全性，只是把数据压小，省带宽。DLMS 规定：

  • 是否压缩由 SC 字节的 bit7 指示（§9.2.7.2.4.2）。
  • 压缩发生在加密之前；接收方先解密、再解压。
  • Suite 0 没有压缩算法，所以 Suite 0 的 SC bit7 没有意义。

练习 1：把 Table 48 的 IC 从 01234567 改成 01234568，哪些值会变？

IV 变（…614E01234568），所以密文和 tag 都会变；EK/AK/APDU 不变。若只变 system title，同样密文与 tag 都变。若只变 AK，则只有 tag 变，密文不变（因为 AK 只进 AAD）。这个对照能帮你定位“到底哪一段错了”。

练习 2：为什么仅认证模式下，APDU 是明文却仍然安全？

“安全”在这里只指完整性与来源认证，不包括保密。APDU 明文可见，但任何改动都会让 tag 验证失败；攻击者没有 AK 就造不出新 tag。若业务要求连“读了哪个对象”都不能泄露，就必须用认证+加密。

练习 3：AES-KW 包装 32 字节的 Suite 2 密钥，输出多长？

32 字节 = 4 个 64-bit 块，输出 5 个块 = 40 字节。记住公式：输出 = 输入 + 8 字节，与 KEK 是 128 还是 256 位无关。

Q1 · DLMS 的 GCM IV 由哪两部分拼成？

  • 发送方 system title（8 B）‖ 发送方 invocation counter（4 B）
  • 接收方 system title（8 B）‖ 接收方 invocation counter（4 B）
  • 随机数（8 B）‖ 时间戳（4 B）

解析：§9.2.3.3.7.3：固定字段是 system title，调用字段是 IC；加密时用发送方自己的，解密时用报文里带的对端 IC。用错方向是“tag 对不上”的头号原因。

Q2 · 仅加密模式（SC=0x20）的报文里，认证 tag 在哪里？

  • 没有 tag：DLMS 不计算也不校验它
  • 有 12 字节 tag，附在密文后
  • 有 16 字节 tag，附在密文前

解析：§9.2.3.3.7.1 明确：仅加密时 tag 不计算、不校验。通用 GCM 库内部可能仍会算出一个值，但协议既不携带也不使用它。

Q3 · Suite 2 的 GCM tag 长度是多少？

  • 96 bit（12 字节），与 Suite 0/1 相同
  • 128 bit（16 字节），随密钥一起增强
  • 256 bit（32 字节），与 EK 等长

解析：§9.2.3.3.7.6：Suite 0、1、2 的 tag 均为 96 bit。Suite 2 增强的是 EK/AK/KEK 长度、曲线与哈希。

Q4 · KDF 里 PartyUInfo 与 PartyVInfo 的顺序写反，会怎样？

  • 派生出的密钥完全不同，双方对不上
  • 没有影响，KDF 会自动排序
  • 只有 Suite 2 受影响，Suite 1 不受影响

解析：OtherInfo 是按字节参与哈希的，顺序变了输入就变了。C.2 的两个方向分别得到 59A71FD8… 与 F0184BDA…，可作为对照。

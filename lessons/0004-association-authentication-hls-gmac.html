第 4 课· 约 18 分钟· 前置：第 1、2 课· 产出：能算一条 GMAC 认证值，能说出四趟 HLS 谁给谁发什么

association 认证：三个等级、四趟 HLS，与能算出来的 GMAC

为什么学这个：前两课处理的都是报文（Phase 2 的数据交换）。但建链时还有个更基本的问题—— 对面到底是不是那台表？这就是 association 建立（AA）阶段的"认证"（Phase 1）。 抓包里 AARQ 里带着一段挑战值、后面又跟着 reply_to_HLS_authentication 的方法调用，就是这一课的内容。
本课唯一要带走的一句话

认证（authentication）与加密（ciphering）是两件正交的事。 认证解决"你是谁"，发生在 AA 建立阶段、由 COSEM-OPEN 服务与 reply_to_HLS_authentication 方法承载； 加密解决"别人看不看得见"，发生在 Phase 2 的报文里。 规范 §9.2.2.2.2.1 原文：“Even in the case where no client-server authentication takes place, cryptographically protected APDUs can be used.” ——没有认证，照样可以用受保护的报文；反过来，认证过了也不等于后面的报文会加密。

1三个认证等级：先立坐标系

§9.2.2.2.2.1 把认证分成三个等级。注意"等级"这个词：它们不是套件（Suite 0/1/2），也不是安全策略位图，而是 AA 建立时用什么手段证明身份。

§9.2.2.2.2 · 三种 authentication security level（§9.4.2.2.3 Table 83 给出 mechanism_id）
等级怎么做几个来回mechanism_id
no security
(Lowest Level Security)		 不认证。客户端可在当前 AA 的安全上下文与访问权限内读一些基本信息 — 0
LLS
(Low Level Security)		 客户端把口令（secret）交给服务端，服务端比对 1 趟（口令随 AARQ 走） 1
HLS
(High Level Security)		 双方各发一个挑战值、各自对对方的挑战做密码学处理，互相验证 4 趟 2…7

关键差别：LLS 是单向的——只有服务端验客户端（对应 ITU-T X.811 的 "unilateral authentication, class 0"）； HLS 是双向的——双方都要成功验证对方，AA 才建立（X.811 的 "mutual authentication using challenge mechanisms"）。这条出处是 §9.2.2.2.2.1 的 NOTE 1 与 NOTE 2。

为什么 HLS 值得多花三趟

LLS 的口令一旦被抓包就永久失守（而且口令是静态的）。HLS 每趟交换的都是随机挑战值， 每次建链都不一样——所以抓到的历史报文对攻击者没用。这是"HLS 比 LLS 高级"的实质，而不只是"加密更强"。

2四趟 HLS：谁在第几趟发什么

§9.2.2.2.2.4 逐字规定了四趟。这张图是本课的骨架——把每条报文归到哪一趟、装在哪，都写清楚了：

§9.2.2.2.2.4 · HLS 四趟（Table 50 的 "Carried by" 行给出承载 APDU）
趟方向带什么装在哪个 APDU 里
Pass 1客户端 → 服务端挑战值 CtoS（+ 视机制而定的附加信息）AARQ（COSEM-OPEN.request）
Pass 2服务端 → 客户端挑战值 StoC（+ 附加信息）AARE（COSEM-OPEN.response）
Pass 3客户端 → 服务端处理结果 f(StoC)调用 reply_to_HLS_authentication 方法（xx.request）
Pass 4服务端 → 客户端处理结果 f(CtoS)该方法的返回（xx.response）
一条必须实现的检查（否则是漏洞）

§9.2.2.2.2.4 原文：“If StoC is the same as CtoS, the client shall reject it and shall abort the AA establishment process.”
——若服务端回的 StoC 与客户端发的 CtoS 相同，客户端必须拒绝并中止 AA。 为什么？因为挑战值必须是对方新生成的随机数；如果它反弹回来，说明对面根本没生成随机数（可能在重放）， 双向认证就退化成"我给自己的值签名再验一遍"，毫无意义。

规范的 Pass 2 与 Pass 3 之间还有一句容易被忽略的：Pass 2 之后，服务端才授权客户端访问 reply_to_HLS_authentication 方法（§9.2.2.2.2.4）。 也就是说第 3、4 趟本身是在"部分建立的 AA"里跑的——这也是为什么这两个方法调用可能已经被加密保护。

3七个 mechanism：同一套四趟，换的是 f() 怎么算

四趟的流程固定，变的是处理挑战的函数 f。§9.2.7.4 Table 50 给出 HLS 的全部六种（mechanism 2–7），名字由 §9.4.2.2.3 的 Table 83 定义：

Table 50（§9.2.7.4, p.260–261）与 Table 83（§9.4.2.2.3, p.313）
id名字f(StoC) / f(CtoS)评价
2HLS（厂商自定） 规范保密（"Man. Spec."） 方法不公开。NOTE 1：处理方式保密
3HLS MD5 MD5(StoC ‖ HLS Secret) 规范明确不推荐新实现使用

4HLS SHA-1 SHA-1(CtoS ‖ HLS Secret)

三条读表要点

① 3 与 4 不要用。Table 50 脚注 1 原文：“The use of authentication mechanisms 3 and 4 are not recommended for new implementations.” MD5 / SHA-1 早已不安全。看到老设备用它们，属于遗留兼容，不要照抄到新实现。
② mechanism 6 与 7 的输入串顺序是"先自己、后对方"。SysT-C ‖ SysT-S 是客户端方向； 响应方向而是 SysT-S ‖ SysT-C（Table 50 的两列就是反的）。这里写反了，现象就是"签名/哈希验不过"。
③ mechanism 5（GMAC）的 IV 规范没在 Table 50 里写。它是靠 Table 51 的例子反推的——见下面第 4 节，这是本课最"动手"的一段。

4动手：把 Table 51 的两条 GMAC 算出来

Table 51 给了 mechanism 5 的完整测试向量——这是本课程第三次"自带标准答案"的机会（前两次是 Table 48 与 Annex C）。我用普通 AES-GCM 原语独立复算，两条都对上了：

怎么算的（这正是第 1 课"仅认证"那一档）：

AAD = SC ‖ AK ‖ 挑战值       ← 被认证的明文字节
P   = （空）                  ← 没有任何东西被加密
T   = GMAC(AAD) 截前 12 字节  ← tag = 96 bit
f   = SC ‖ IC ‖ T             ← 17 字节，SC 与 IC 明文照带
复算中我自己踩到的坑（值得你知道）

我一开始以为 IV 用的是发出挑战的一方的 system title——算出来两条都对不上。 枚举之后才确定：IV 用的是"算这一趟的那一方"（本端）的 Sys-T ‖ IC。
客户端算 f(StoC) → 用客户端的 Sys-T ‖ IC，得到 4D4D4D000000000100000001，IC 是客户端自己的 00000001； 服务端算 f(CtoS) → 用服务端的 Sys-T ‖ IC，IC 是 01234567。
这与我最初"用挑战发起方"的直觉正好相反。怎么才能自己发现？看 Table 51 里 f(x) 的封装： f(StoC) = 10 00000001 …、f(CtoS) = 10 01234567 …——IC 直接印在那里，正好是各自的本端计数器。 这就是"自带标准答案"的价值：猜错了立刻被向量驳回。

这里有一个规范没写清的空白（诚实标注）

Table 50 只写了 f 的输出形式 SC ‖ IC ‖ T，没写这个 IC 取自哪里、按什么规则递增； IV 的构造在 §9.2.7.4 里也没有像 §9.2.3.3.7.3（ciphering 报文）那样明说。 上面的结论是我从 Table 51 的例子反推的（虽然两条向量高度一致，可信度高），不是规范明文。 实现侧还多一层：Gurux 有个 IncreaseInvocationCounterForGMacAuthentication 开关（默认 true）， 意味着"算 GMAC 时要不要顺便把计数器加一"在实现之间可能不一致。对接具体设备时，这一条必须实测，别照抄任何一方。

5挑战值被打包在哪里：APDU 与"附带信息"

挑战值不是裸的随机数——它还可能需要附带 system title、证书。载体是两个看起来不相关、其实专门为此准备的字段（§9.4.4.1）：

§9.4.4.1 · AARQ / AARE 里与安全相关的字段
字段装什么在哪个 APDU
calling-AP-title客户端的 system title（用了 ciphering 时必须带）AARQ
calling-AE-qualifier客户端数字签名密钥的公钥证书AARQ
responding-AP-title服务端的 system titleAARE
responding-AE-qualifier服务端的公钥证书AARE

Table 50 的 NOTE 说得很清楚：“The system titles and the Certificates have to be sent only if not already known by the other party.” ——已知道就不用再发（比如以前在注册流程里发过）。但如果对方没有这些材料，挑战就处理不了，§9.2.7.4 原文：“the result of the processing of the challenge fails and the AA shall not be established.”

另外，机制 7（ECDSA）的挑战值长度是 32–64 字节，而 2–6 是 8–64 字节（Table 50 的 Pass 1/2 列）。ECDSA 需要签名，长度要求自然更硬。

6练一下

Q1 · 关于"认证"与"加密"的关系，哪一句正确？

  • 两者互相独立，可分别启用
  • 认证成功即报文自动加密
  • 加密后无需再做认证
  • 两者必须同时启用或同时关闭

解析：§9.2.2.2.2.1 原文明确两者独立：认证在 Phase 1（AA 建立），加密在 Phase 2（报文）；"Even in the case where no client-server authentication takes place, cryptographically protected APDUs can be used." 所以既可能"认证了但报文明文"，也可能"没认证但报文加密"。把两者绑在一起理解，会在配置安全策略时踩坑。

Q2 · 服务端回的 StoC 与客户端发的 CtoS 一模一样，客户端应该怎么做？

  • 拒绝并中止 AA 建立
  • 照常计算并回送结果
  • 把挑战值加一再计算
  • 改用 LLS 口令继续

解析：§9.2.2.2.2.4 的硬规定："If StoC is the same as CtoS, the client shall reject it and shall abort the AA establishment process." 原因：挑战值必须是对方新生成的随机数。若它是把客户端自己的值原样弹回，双向认证就名存实亡——你只是在验自己发的值，任何人都能这么做。这是防重放的关键一步。

Q3 · mechanism 5（HLS GMAC）里，T = GMAC(SC ‖ AK ‖ StoC) 用的是什么 IV？

  • 计算方自己的 Sys-T ‖ IC
  • 发起方（客户端）的 system title
  • 被认证内容的哈希前 12 字节
  • 不使用 IV，GMAC 无需 IV

解析：本课第 4 节的复算结论：客户端算 f(StoC) 用客户端的 Sys-T ‖ IC，服务端算 f(CtoS) 用服务端的。我从 Table 51 的两条向量反推、枚举验证过（IV 用错则两条都对不上）。但要注意：规范 §9.2.7.4 没有像 §9.2.3.3.7.3 那样明写这条，IC 的递增规则也未规定——所以我把它标为"反推 + 实测为准"。GMAC 和所有 GCM 一样是需要 IV 的，"不需要 IV"是错的。

闭卷三问

1 · 不看资料，写出 HLS 四趟的方向与承载 APDU。

Pass 1 客户端→服务端，CtoS，装在 AARQ；Pass 2 服务端→客户端，StoC，装在 AARE； Pass 3 客户端→服务端，f(StoC)，装在 reply_to_HLS_authentication 方法调用；Pass 4 服务端→客户端，f(CtoS)，是该方法的返回。
依据：§9.2.2.2.2.4 与 Table 50 的 "Carried by" 行。

2 · mechanism 6（SHA-256）与 mechanism 7（ECDSA）的输入串，两个方向为什么不同？

因为它们是不对称的：谁在算，就要把自己放前面。
f(StoC)（客户端算）：SysT-C ‖ SysT-S ‖ StoC ‖ CtoS；f(CtoS)（服务端算）：SysT-S ‖ SysT-C ‖ CtoS ‖ StoC——两个方向连挑战值的顺序也反过来。
这样两趟算出的结果必然不同，无法把一个方向的结果挪用到另一个方向。依据：Table 50。

3 · 为什么规范说 MD5 / SHA-1 两套 mechanism "不推荐"？

Table 50 脚注 1："The use of authentication mechanisms 3 and 4 are not recommended for new implementations." MD5 与 SHA-1 都已存在实际可行的碰撞攻击，且它们只做简单哈希、不像 GMAC/ECDSA 那样基于当前套件的密钥材料。老设备可能有，新实现应选 5/6/7。

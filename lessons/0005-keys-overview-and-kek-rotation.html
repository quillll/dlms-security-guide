第 5 课· 约 17 分钟· 前置：第 3、4 课· 产出：能按用途与建立方式给六把对称密钥归类，能说清 KEK 轮换的顺序

密钥全貌：六把对称密钥从哪来，KEK 为什么要"自己包自己"

为什么学这个：前四课里密钥是"给定"的（EK、AK 直接用）。但真实设备上， 这些密钥怎么进到表里？换了怎么通知对方？——这是运维与对接的真正工作。 这一课把所有对称密钥一次理清，并讲清 DLMS 里唯一"密钥管理"的机制：key_transfer + KEK 包装。
本课唯一要带走的一句话

DLMS 的对称密钥体系是一棵以 master key（KEK）为根的树： KEK 通过带外预置，其余所有密钥（GUEK / GBEK / GAK / 临时密钥，乃至 KEK 自身的更新）都用 AES key wrap 由 KEK 包装后传输。 所以"换密钥"这件事，永远是"用旧 KEK 包新密钥"；连换 KEK 也是"用旧 KEK 包新 KEK"。

两个最容易混的点

① "AK" 在规范里的正式名是 GAK。我们前几课口头说的 "AK"，Table 28 里叫 (Global) Authentication Key, GAK。 代码里常写 AuthenticationKey——同一个东西。GUEK / GBEK / GAK 都由 "Security setup" 对象持有（Table 28 脚注 1、2）。

2三条建立路径：预置、包装、协商

Table 28 的"Key establishment"一列只有三种值。理解这三条路，就理解了设备上密钥是怎么落地的：

① Out of band带外预置。出厂/装表时人工配。
只有 master key 能这么来
→
② Key wrapping用 KEK 把随机生成的新密钥包起来传（§9.2.5.4）。
靠 key_transfer 方法
→
③ Key agreement现场协商（§9.2.5.5）。
靠 key_agreement 方法，C(2e,0s)

三条路的关键区别在于"信任从哪来"：

  • 带外：信任来自运维过程（谁装的表、谁给的密钥）。规范对这条没有技术描述，因为它发生在协议之外。
  • 包装（key wrapping）：信任来自"双方已经共享 KEK"。算法是 AES key wrap（§9.2.3.3.8 / RFC 3394）， KEK 就是 master key（§9.2.5.4 原文：“The KEK is the master key. Consequently, this method can be used only between parties sharing the master key.”）。
  • 协商（key agreement）：信任来自"双方各自的静态密钥对 + 可选的证书"。这就是第 3 课的 ECDH 家族。

3key_transfer：密钥分发长什么样

§9.2.5.4 规定：要分发静态密钥，必须由客户端先生成，然后用 key_transfer 方法送给服务端。 方法参数的结构在蓝皮书 §4.4.7.3.2（p.136）——注意 key_id 的取值就是 Table 28 前四把密钥：

data ::= array  key_transfer_data

key_transfer_data ::= structure
{
    key_id: enum:
        (0) global unicast encryption key,      // GUEK
        (1) global broadcast encryption key,    // GBEK
        (2) authentication key,                 // GAK
        (3) master key (KEK)                    // ← 连 KEK 自己也走这条路
    key_wrapped: octet-string                   // 用 KEK 做 AES key wrap 的结果
}

两个实操要点（都来自规范原文）：

  • 可以一次传多把：用 n 个元素的数组一次调完，或者调 n 次、每次只传一把（NOTE 1）。
  • 失败即全不变：“If the unwrapping of the key(s) is not successful, the method invocation fails … The keys are not changed.”（§4.4.7.3.2） ——解包失败不会部分写入，这一点对"换密钥换了一半"的灾难场景很重要。

4KEK 轮换：为什么是"用旧 KEK 包新 KEK"

现在到本课的核心。既然 key_id 里有 (3) master key (KEK)，说明 KEK 自己也是可以被 key_transfer 传送的。 但传送它需要 KEK——这不就是"鸡生蛋"吗？

答案是：用旧 KEK 包新 KEK，然后立刻切换

轮换的顺序是固定的，漏掉任何一步都会把设备锁死：

  1. 客户端生成新 KEK；
  2. 用当前（旧）KEK做 AES key wrap，把新 KEK 包起来；
  3. 通过 key_transfer 发送，key_id = 3；
  4. 服务端用旧的 KEK 解包，拿到新 KEK——解包成功说明客户端确实持有旧 KEK；
  5. 服务端回 success，新 KEK 立即生效。

第 5 步的"立即生效"是规范明文（§4.4.7.3.2）：“The new keys are activated immediately after result of the method invocation is sent back with result = success. Notice that this rule equally applies to all keys, including the master key.” ——连 master key 也一样。

顺序错一步的两个典型事故

① 先切 KEK、后发报文。如果客户端先把本地的 KEK 换成新的再去调用 key_transfer， 服务端还在用旧 KEK 解包 → 解包失败、密钥不变，而客户端以为换好了。之后所有通信都用错密钥。
② 忘记"立即生效"。新 KEK 在服务端回 success 的同一刻就已经生效， 所以紧接着的下一条报文就必须用新 KEK 保护。任何"等服务端再确认一次"的缓冲逻辑都会失败。

规范还留了一句兜底（NOTE 3）：“If using the new keys fails, the client may try to recover … by reverting to using the previous keys or repeating the key transfer process.” ——即客户端应保留旧密钥以便回滚。但既然新 KEK 已生效，回滚本身也要用新 KEK 走一遍 key_transfer 把旧的包回去。规范没展开这个细节，属于实现的判断空间。

5把四课串起来：一条报文用到了哪几把密钥

这套体系最容易"一看就懂、一用就乱"的地方是：一条报文可能同时涉及多把密钥，各司其职。拿第 3 课那条 general-ciphering 报文举例：

同一条 general-ciphering 报文里，每把密钥的角色
密钥在这条报文里做什么
KEK（master key）包装 key-info 里携带的内容（如果 key-info 是 wrapped-key）——保护"密钥本身"
临时密钥 / GUEK真正加密 ciphered-content 里那段 APDU——保护"数据"
GAK（AK）进入 AAD，用于计算 ciphered-content 尾部的认证 tag——保护"完整性"
system title作为 IV 的前 8 字节；同时决定用哪套密钥——标识"谁"
IC作为 IV 的后 4 字节，保证同一密钥下每条报文的 IV 都不同——防重放

所以"密钥分层"的意义是：换临时密钥不用动 KEK，换 GUEK 不用换表；而 KEK 只在需要换 GUEK/GAK/KEK 本身时才用到。 这就是为什么 KEK 只做"包装"一件事——它出现得越少，泄漏窗口越小。

6练一下

Q1 · 哪把密钥在规范里只能"带外（out of band）"建立？

  • master key（KEK）
  • global unicast encryption key
  • dedicated key
  • ephemeral encryption key

解析：Table 28 里只有 master key 那一行有 "Out of band" 这一建立方式（它还有 key wrapping 与 key agreement 两条，用于更新）。原因是结构性的：KEK 是包装其它密钥的根，它自己无法被任何密钥包装。初始的 KEK 只能靠带外预置——这也是为什么装表时"抄密钥"这个动作不可省。

Q2 · 用 key_transfer 换 KEK 时，新 KEK 应该用哪把密钥包装？

  • 旧的（当前生效的）KEK
  • 新 KEK 自己包装自己
  • 用 GAK 包装
  • 用服务端的公钥包装

解析：§9.2.5.4 明确 "The KEK is the master key"——包装永远用当前共享的 KEK，也就是旧的。用新 KEK 自包对方解不开（除非对方已知新 KEK，那就失去意义了）。GAK 只进 AAD、不做包装；DLMS 不用公钥直接加密密钥（那是 ECDH 协商的领域，是另一条路）。

Q3 · key_transfer 失败（解包不成功）后，设备上的密钥处于什么状态？

  • 全部保持原样，一把都不变
  • 已解开的先生效，其余不变
  • 全部被清零，需重新预置
  • 回退到出厂默认密钥

解析：§4.4.7.3.2 原文：“If the unwrapping of the key(s) is not successful, the method invocation fails and an appropriate reason for the failure shall be sent back. The keys are not changed.” 这是原子性保证——即使一次传了多把密钥，部分失败也不会部分生效。正是这条让"换密钥"变得可重试、可回滚。

闭卷两问

1 · 不看资料，说出六把对称密钥的名字与各自一句话用途。

master key / KEK——包装其它密钥（根）；GUEK——单播加密密钥；GBEK——广播加密密钥； GAK——进 AAD 做认证；dedicated key——AA 内单播加密密钥，随 Initiate.request 传送； ephemeral key——一次性加密密钥。依据：Table 28（§9.2.5.1, p.230）。

2 · 为什么说 KEK 是"用得越少越好"？

因为 KEK 唯一职责是包装其它密钥，不参与任何数据加解密。日常报文用临时密钥或 GUEK，用不到它； 它只在换密钥时出现。所以把 KEK 单独保管、少用，可以把"根密钥泄漏"的暴露面压到最小——这正是密钥分层的意义（§9.2.5.4 / Table 28 的 Use 列）。

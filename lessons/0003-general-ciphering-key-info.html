第 3 课· 约 16 分钟· 前置：第 1、2 课· 产出：能拆 general-ciphering 的两层结构，看懂 key-info

general-* 家族：报文里怎么"顺便"带上一把密钥

为什么学这个：第 2 课那条报文只能保护"服务特定"的几种 APDU，而且密钥必须提前配好。一旦要做密钥分发或现场协商，就必须用 general-* 家族——它能在报文里说明"这次用哪把密钥"。抓包里看到 DD 开头的长报文，就是它。
本课唯一要带走的一句话

general-ciphering 是两层结构：外层是"寄件信息"（transaction-id ‖ 两端 system title ‖ date-time ‖ other-information ‖ key-info）， 里面那层 ciphered-content 才是第 2 课学的 SH ‖ 内容 ‖ tag。 key-info 是这一族独有的——正是它让"报文里顺带送一把密钥"成为可能。

绿皮书 Table 47（§9.2.7.2.4.9, p.254）把受保护 APDU 分成三族，"谁有哪些字段"一目了然：

2拆一条真的：Annex C.2 的 401 字节请求

里层（235 字节）就是第 2 课那套结构：

31 00000000 ‖ 218 字节密文 ‖ 9836002AEA6E7012D2ADFAA7
│  │           │              └─ 12 字节认证 tag
│  │           └─ GCM 输出的密文
│  └─ IC = 0（新密钥建立时计数器归零，§9.2.7.2.4.9）
└─ SC = 0x31 → 套件 1（低半字节）+ 认证 + 加密（bit4、bit5）
两个真实存在的坑

① 00 不等于"字段不存在"。date-time 与 other-information 在这里是"字段存在、长度 0"。 按固定偏移取字段的解析器最容易在这里错位——所以这族报文必须逐字段按长度推进，不能算死偏移。
② 81 80 不是数据，是长度。≥128 字节的字段用长形式（0x81 xx / 0x82 xx xx）。 把 81 当成第一个数据字节，后面全错。

3key-info 的三种可能：报文里到底在说哪把密钥

§9.2.5.2 Table 29 把 key-info 定义成一个 CHOICE（ASN.1 见 §9.5）：

Table 29 · key information
选择CHOICE 值里面装什么什么时候用
identified-key0 key-id：0 = GUEK（单播），1 = GBEK（广播） 密钥两端都已持有，只是指出用哪一把。通用加密报文之间互传时最常用
wrapped-key1 kek-id（0 = master key）+ key-ciphered-data 把随机生成的密钥用 KEK 包起来送过去（RFC 3394 AES key wrap）——密钥分发
agreed-key2 key-parameters + key-ciphered-data 现场协商：只在这族出现，本课例子用它

key-parameters 的取值只有两个（Table 29）：

0x01 → C(1e, 1s, ECC CDH)  One-Pass Diffie-Hellman   // 一方临时密钥 + 一方静态密钥
0x02 → C(0e, 2s, ECC CDH)  Static Unified Model       // 双方都用静态密钥（+ NonceU）

注意：第三种方案 C(2e, 0s)（双方都用临时密钥）不在这张表里——它是通过 key_agreement 方法协商主密钥/全局密钥的，不是塞在单条报文的 key-info 里（见 §9.2.3.4.6.2 与 §9.2.5.5）。

规范的默认选择与一条安全警告

默认用哪个：§9.2.5.5 逐字写着 “Unless specified otherwise in a project specific companion specification, the C(1e, 1s ECC CDH) scheme shall be used.” ——除非项目规范另有规定，就该用 One-Pass DH。
为什么不用静态方案：Table 24 的 NOTE 2 说得很重——C(0e,2s) 下 Z 在所有交易中恒定不变，一旦泄漏， 用同一对静态密钥协商出的过去、现在、未来的密钥材料都可能被攻破；未"零化"的 Z 必须按私钥级别保管。

从这四行里读出一件事（先想再展开）

C.2 的两个方向，Z 不同、system title 顺序还相反——为什么必须这样？

因为 KDF 的 OtherInfo = AlgorithmID ‖ PartyUInfo ‖ PartyVInfo（§9.2.3.4.6.5）：发起方把自己放在 PartyU、把对方放在 PartyV。 同一对实体在两个方向上算出的密钥必须不同，否则双向流量会共用密钥与密钥流。
这也是实现里最常见的错误来源：把顺序写反，密钥就完全不同——现象是"密钥协商成功、但对方说 tag 校验失败"。 我在脚本里就是靠这两条向量确认顺序的。

6练一下

Q1 · general-ciphering 里 key-info 的作用是？

  • 指明或协商本帧密钥
  • 指明报文的访问权限
  • 指明报文的压缩方式
  • 指明发起方的计数器

解析：key-info 是一个 CHOICE（§9.2.5.2 Table 29）：identified-key 只指出用哪把已持有的全局密钥，wrapped-key 用 KEK 包一把新密钥送过去，agreed-key 现场协商。访问权限在 Association 对象里、压缩在 SC 的 bit7、计数器是 SH 里的 IC——都不是 key-info 的职责。

Q2 · C(0e, 2s) 方案的主要安全弱点是？

  • 共享秘密长期不变
  • 每次都要新密钥对
  • 只能协商临时密钥
  • 无法验证对端身份

解析：双方都用静态密钥，所以 Z 恒定（Table 24 NOTE 2）：一旦泄漏，用同一对静态密钥派生过的历史、当前与未来密钥材料都可能失效。规范因此要求：除非项目规范另有规定，应优先用 C(1e,1s)。"每次都要新密钥对"是临时方案（C(2e,0s)）的特点，不是弱点；身份验证靠 ECDSA 证书，与用哪种 ECDH 方案无关。

Q3 · general-glo-ciphering 为什么不需要 key-info？

  • 用已约定的全局密钥
  • 每次都现场协商密钥
  • 用报文头携带的密钥
  • 完全不需要任何密钥

解析：Table 47 里 key-info 一栏只有 general-ciphering 是 "+"。general-glo/ded 用的是两端事先约定好的全局/专用密钥（GUEK / 专用密钥），所以报文只需带上 system-title 表明身份，不需要再讨论用哪把密钥。它还是一种"轻量"选择：外层字段更少。

闭卷三问

1 · 不看资料，写出 general-ciphering 的外层字段顺序。

Tag(0xDD) → transaction-id → originator-system-title → recipient-system-title → date-time → other-information → key-info → ciphered-content。
依据：§9.2.7.2.4.8 Figure 109 与 Table 47。每个字段都是「长度 + 值」，长度可能是长形式。

2 · 报文里出现 00 当作 date-time 字段，是什么意思？

字段存在但长度为 0，即本次没有携带时间戳。解析器必须按长度推进（读 1 字节长度、再跳过 0 字节），不能把 00 当成"字段不存在"而少推一位，也不能按固定偏移去取后面的字段。

3 · key-parameters 的 0x01 与 0x02 分别是什么？为什么 0x02 需要 transaction-id？

0x01 = C(1e, 1s, ECC CDH)（One-Pass DH）；0x02 = C(0e, 2s, ECC CDH)（Static Unified）。
静态方案双方的共享秘密 Z 每次都一样，所以必须靠一个每次不同的输入来区分——规范就用 transaction-id 充当 NonceU（§9.2.3.4.6.4 步骤 5），并把它放进 KDF 的 PartyUInfo。这也是为什么 0x02 的 key-ciphered-data 是空的：没有临时公钥要传。

第 6 课· 约 16 分钟· 前置：第 1、5 课· 产出：能定位安全配置所在的对象，能读出策略/套件并解释其含义

Security setup 实操：读哪几个属性，调哪几个方法

为什么学这个：这是把前五课"落到设备上"的最后一公里。 你对接真实表计时，第一个要 read 的对象不是数据点，而是 Security setup—— 它决定了当前 AA 用哪个套件、要求什么保护。不会读这三个属性，就无法判断一台表到底安不安全。
本课唯一要带走的一句话

Security setup 是"每个 Association 一个"的对象（class_id = 64，OBIS 0-0:43.0.e.255）， 它用属性 2 security_policy 声明"对请求/响应各要求哪种保护"、 用属性 3 security_suite 声明"允许用哪套算法"。 前者是"要求"，后者是"能力"——两者是独立的旋钮（这正是第 1 课立下的坐标系在设备上的落点）。

1先找到它：OBIS 与"每个 AA 引用一个"

蓝皮书 §6.2.36（p.656）规定：“For each Association object, there is one Security setup object managing security within that AA.” ——每个 Association 对象引用一个 Security setup 来管理该 AA 的安全。注意这是“引用关系”，不是“一一对应”：不同 AA 可以共享同一个 Security setup，也可以各用各的（Table 28 注 1）。它的 OBIS 用 A/B/C/D/E/F 六段表示（转换稿里是按列拆开的表格，不是连写字符串）：

§6.2.36（p.656）· 安全相关对象的 OBIS
对象ICABCDEF
Security setup6400430e255
Attestation1700b433e255
Invocation counterData0b431e255

读出三件事：

  • C 段 = 43 标识"安全相关对象"这一类（6.2.36 列在 value group 43 下）。
  • E 段 = e 是实例编号（由设备配置决定，不是“第几个 AA”的固定映射）；规范要求 “The value in value group E shall be the same as in the logical name of the corresponding Security setup object.” ——即 Invocation counter 的 E 段与它对应的 Security setup 必须一致，这是配对键。
  • Invocation counter 是 Data 类的对象（不是独立类），B 段标识通信通道——“The same client may use different communication channels e.g. a remote port and a local port. The invocation counter on the different channels may be different.” 所以同一个客户端走远程口和本地口，计数器是分开的。这是排查"IC 对不上导致 tag 校验失败"的关键线索。
常见误判（我先前的踩坑）

这两条 OBIS 在转换稿里搜不到连写字符串（如 0-0:43.0.e.255），因为它们以"六列各一格"的表格形式存在。 用文字搜索会误以为规范没规定——实际规定得很明确。查 OBIS 时要按列读表格，不要只搜冒号格式的字符串。

属性 2 与 3 是本课的核心，逐个讲。

属性 2 · security_policy：8 个 bit，请求响应各一半

§4.4.7.2.2 规定它是一个 enum，按无符号数解释时每个 bit 的含义如下（“It applies independently for requests and responses.”）：

§4.4.7.2.2（p.133）· security_policy 位图
bit含义bit含义
0未使用，必须置 04digitally signed request（请求签名）
1未使用，必须置 05authenticated response（响应认证）
2authenticated request（请求认证）6encrypted response（响应加密）
3encrypted request（请求加密）7digitally signed response（响应签名）

所以 bit 2–4 管"客户端发出去的"（request），bit 5–7 管"服务端回的"（response）。举几个值：

0x00 = 0   → 不要求任何保护（= version 0 的行为，见下）
0x04 = bit2 → 仅要求请求被认证
0x0C = bit2+bit3 → 请求要认证 + 加密
0x1C = bit2+3+4 → 请求要认证 + 加密 + 签名
0x44 = bit2+6 → 请求认证、响应加密（不对称配置）
一句容易读漏的原文

§4.4.7.2.2 最后一行：“The access rights may require stronger protection than what is required by the security policy.” ——访问权限（access rights）可能比安全策略要求更高。也就是说，即使 policy 说"不要求加密"， 某个对象的访问权限仍可能要求加密。最终生效的保护是"策略"与"访问权限"里更强的那一个。 排障时只读 policy 是不够的——这解释了"policy 看着没要求加密，报文却加密了"的现象。

属性 3 · security_suite：只有 0/1/2 有定义

§4.4.7.2.3 逐字：

(0) AES-GCM-128 认证加密 + AES-128 key wrap
(1) AES-GCM-128 认证加密、ECDSA P-256 签名、ECDH P-256 协商、
    SHA-256、V.44 压缩、AES-128 key wrap
(2) AES-GCM-256 认证加密、ECDSA P-384 签名、ECDH P-384 协商、
    SHA-384、V.44 压缩、AES-256 key wrap
(3) … (15) reserved

这就是第 1 课 Table 27 在设备侧的回声——套件编号的取值域在这里被固定为 0/1/2，其余保留。 注意 (0) 里没有非对称算法、没有 V.44 压缩：这正是"Suite 0 只做对称"的落地形式。

version 0 与 version 1 的差别（容易踩）

Security setup 的 version = 1 才有完整的属性 2–6 与方法 1–8。version 0 的对象要弱得多： §4.4.7.2.2 的 NOTE 原文：“With this, the value (0) means that no cryptographic protection is required, as in version 0 of the ‘Security setup’ IC.” ——即 version 0 只有 security_policy = 0 这一种状态。
实操含义：对接老表时，先读 version 与 security_suite。 如果 security_suite 只能读到 0，那它很可能只能做 Suite 0——不要指望在上面配 Suite 1/2 的证书和签名。

3方法 1–8：能对设备做的八个动作

§4.4.7.1（p.133）· Security setup 的 specific methods（全部为 optional，o）
#方法做什么Short name相关课
1security_activate (data)强化安全策略（只能加强，不能削弱）x+0x30本课 §4
2key_transfer (data)用 KEK 包装后传送对称密钥x+0x38第 5 课
3key_agreement (data)ECDH 协商对称密钥（C(2e,0s)）x+0x48第 3 课
4generate_key_pair (data)在设备内生成非对称密钥对x+0x50—
5generate_certificate_request (data)生成证书请求（CSR，交给 CA 签发）x+0x58—
6import_certificate (data)导入证书x+0x60—
7export_certificate (data)导出证书x+0x68—

读法：方法 2、3 是第 5 课讲的"密钥从哪来"的两条路（包装 / 协商）； 方法 4–8 是设备内自建 PKI 流程——先在表里生成密钥对、再生成 CSR、拿去 CA 签完导入。这说明 非对称密钥可以在表内生成，私钥不必离开设备，这是比"外部生成再导入"更安全的做法。

4security_activate：为什么只能加强、不能削弱

这是本课最值得记住的方法行为。§4.4.7.3.1（p.135）三段话，每句都是设计意图：

data ::= enum, as specified at the security_policy attribute.
  • 它接收的就是 security_policy 那种 enum（同一套位图）。
  • “Strengthening the security policy means that another kind of protection is added.” ——"强化"的定义是新增一类保护（认证 / 加密 / 签名 三种之一）。
  • “Once a kind of protection is added, it cannot be removed. If the method is invoked with a value indicating a security policy that is weaker than the value of the security_policy attribute, the method invocation fails.” ——已加的保护不能撤；调用一个更弱的值直接失败。
  • “The new security policy applies as soon as the method invocation has been confirmed with success.” ——成功确认的那一刻立即生效（与第 5 课 key_transfer 的"立即生效"同构）。
这条规则为什么这样设计

安全配置是单向棘轮：只能往更安全的方向走。
否则一台已被攻陷的表可以被悄悄"降级"到无保护状态，然后攻击者就能明文操作它—— 这会让前面所有密钥与认证工作归零。"不可降级"本身就是一道防线。

实操含义：如果你误把策略调得过高（比如要求签名但表不支持），不能靠"调低回去"补救—— 必须换用更高级的凭据完成建链，或走厂商的维护流程。调之前要看清楚。

5对接清单：新接手一台表，按顺序读什么

把前五课压成一份可执行的排障顺序：

  1. 读 security_suite（属性 3） → 知道它支持哪套算法（只读到 0 就别指望 Suite 1/2）。
  2. 读 security_policy（属性 2） → 知道当前要求哪些保护（注意是"要求"，不是"实际"）。
  3. 读 client_system_title / server_system_title（属性 4/5） → 确认身份标识，判断与抓包里的 IV 前 8 字节是否一致。
  4. 读 certificates（属性 6） → 若走 Suite 1/2，看证书是否就位、有没有过期。
  5. 读对应的 Invocation counter 对象 → 拿当前 IC；注意按通道区分（B 段不同）。
  6. 建链时看 AARQ → 用了哪种认证机制（LLS / HLS mechanism 几），见第 4 课。
排障三连（按发生频率排序）

① tag 校验失败 → 先核对 IC（尤其是不是取错了通道的计数器）。
② 密钥协商成功但对方解密失败 → KDF 的 system title 顺序写反了（第 3 课）。
③ "policy 没要求加密，报文却加密了" → 访问权限比 policy 更严（本课 §2 那条原文）。

6练一下

Q1 · 一台表读出的 security_policy = 0x0C，意思是？

  • 请求要被认证并加密
  • 响应要被认证并加密
  • 请求与响应都被认证并加密
  • 不要求任何保护

解析：0x0C = bit2 + bit3。§4.4.7.2.2 里 bit2 = authenticated request、bit3 = encrypted request，而 bit5/6 才是 response 一侧。所以 0x0C 只管请求方向。要响应也保护，得把 bit5/6 也置上（如 0x6C）。这个"请求/响应各一半"的位图布局是读 policy 最容易看错的地方。

Q2 · 想把 security_policy 从"要求认证+加密"改成"只要求认证"，会怎样？

  • 方法调用失败，策略不变
  • 策略成功降级为仅认证
  • 加密被保留，仅认证也加上
  • 策略被清零后重建

解析：§4.4.7.3.1 明文："Once a kind of protection is added, it cannot be removed. If the method is invoked with a value indicating a security policy that is weaker than the value of the security_policy attribute, the method invocation fails." 安全策略是单向棘轮，只能加强。"选项三"混淆了——加强是"新增另一类保护"，不是"保留旧的再加新的"这种可选行为，削弱一律拒绝。

Q3 · 同一个客户端用远程口与本地口连同一台表，Invocation counter 应该？

  • 按通道各自独立计数
  • 两个通道共用一个计数器
  • 只有远程口需要计数器
  • 由服务端统一分配同一个值

解析：§6.2.36 的说明与 OBIS 设计：Invocation counter 对象的 B 段标识通信通道，且 NOTE 明确 "The same client may use different communication channels e.g. a remote port and a local port. The invocation counter on the different channels may be different." 因此两个通道的 IC 是分开推进的。如果你从远程口拿到的 IC 去解本地口的报文，就会 tag 校验失败——这是很常见的对接故障。

闭卷两问

1 · Security setup 的 OBIS 是什么？它和 Invocation counter 用什么配对？

Security setup：0-0:43.0.e.255（class_id 64）；Invocation counter：0-b:43.1.e.255（Data 类，B 段 = 通道）。
两者用 E 段配对：§6.2.36 要求 “The value in value group E shall be the same as in the logical name of the corresponding Security setup object.”

2 · "策略"与"访问权限"是什么关系？为什么排障时两个都要看？

两者独立，最终生效的是更强的那一个：§4.4.7.2.2 明确 “The access rights may require stronger protection than what is required by the security policy.”
只看 policy 会漏判——某个对象的访问权限可能单独要求加密/签名。所以"policy 说不需要保护，报文却被保护了"是正常的，不是配置错误。

Chapter 1

五个旋钮：先把“安全”拆开

一句话直觉：套件是“工具箱”，策略是“必须用哪几件工具”，访问权限是“这个抽屉必须用几件工具才能开”，安全材料是“工具本身”，认证是“进门时怎么验身份”。

1.1 旋钮一：安全套件（security suite）

套件回答：这条连接允许使用哪些算法、密钥多长。它是“能力清单”，不是“保护等级”。取值只有 0 / 1 / 2（3–15 保留）。它存在蓝皮书 Security setup 对象的属性 3（class_id 64），由 Association 对象的 security_setup_reference 引用。

1.2 旋钮二：安全策略（security policy）

策略回答：请求和响应分别“必须”被怎样保护。它是 Security setup 的属性 2，一个 8 位枚举（蓝皮书 §4.4.7.2.2）：

Table 42 · Security policy 位图（Security setup version 1）
bit含义置 1 表示
0unused必须为 0
1unused必须为 0
2authenticated request客户端发来的请求必须带认证
3encrypted request客户端发来的请求必须加密
4digitally signed request请求必须带数字签名
5authenticated response服务端回的响应必须带认证
6encrypted response响应必须加密
7digitally signed response响应必须带数字签名

所以 0x24 读作：bit2+bit5 = 请求要认证、响应要认证；0x6C = bit2+3+5+6 = 请求认证+加密、响应认证+加密；0x3C = bit2+3+4+5 = 请求认证+加密+签名，响应只认证。“0” 才表示完全不要求密码学保护。

1.3 旋钮三：访问权限（access rights）

访问权限回答：具体某个对象的某个属性/方法，在这个 AA 里允许怎么访问、要求什么保护。它不在 Security setup 里，而在 Association 对象的 object_list / access_rights_list 里，每个条目一个字节（Table 43）：

策略与权限的关系：权限可以更严，不能更松

蓝皮书 §4.4.7.2.2 原文：“The access rights may require stronger protection than what is required by the security policy.” 也就是说：策略说“要认证”，权限可以要求“认证+加密”；策略说“要加密”、权限只要求“认证”，实际仍然要加密。判定时把两边的保护位取并集（更严者）。

1.4 旋钮四：安全材料（security material）

材料回答：用哪把钥匙、哪个证书、哪个计数器。至少包括：

  • EK（encryption key，块密钥）、AK（authentication key，只进 AAD）；
  • KEK（master key，包装密钥）、GUEK / GBEK / GAK（全局单播/广播加密密钥、全局认证密钥）；
  • dedicated key（本次 AA 专用）、ephemeral key（一次性）；
  • system title（8 字节设备标识，进 IV 和 KDF）、invocation counter（4 字节计数器）；
  • 证书与私钥（Suite 1/2 才用）。

1.5 旋钮五：认证机制（authentication）

认证回答：建链时，客户端/服务端怎么证明“我是我”。三种等级：No security（最低级）、LLS（口令）、HLS（挑战应答，mechanism 2–7 共六种）。它发生在 AA 建立阶段，和“报文要不要加密”是完全独立的另一件事（见第 7 章）。

1.6 最容易混的六组概念

容易混的正确的区分
Suite 0 vs “不加密”Suite 0 仍强制 AES-GCM-128；不加密由 SC 的 E=0 或 policy=0 决定。
LLS/HLS vs 报文加密前者是建链认证，后者是 phase 2 的报文保护，互相独立。
security policy vs access rights前者是整条 AA 的“最低要求”，后者是逐对象的“更高要求”；取更严。
EK vs AKEK 进 AES 做加密；AK 只进 AAD，不参与加密。
system title vs OBISsystem title 是 8 字节设备标识（进 IV/KDF）；OBIS 是对象标识（6 字节）。
invocation counter vs 帧序号IC 是密码学计数器，进 IV，换钥匙清零；不是 HDLC 帧序号。
第 1 章带走

套件 = 能力；策略/权限 = 要求；材料 = 钥匙；认证 = 身份。排任何安全问题时，先问“是哪一层不满足”，不要一上来就怀疑算法。

Chapter 2

对称算法逐个讲：AES、GCM、GMAC、Key Wrap、SHA、KDF

一句话直觉：AES 是锁；GCM 是“带防拆封条的锁法”；GMAC 是“只贴封条不锁”；Key Wrap 是“装钥匙的信封”；SHA 是“指纹”；KDF 是“把共享秘密加工成能用的钥匙”。

2.1 AES：16 字节一块的锁

AES（FIPS 197）是分组密码：一次处理 128 bit（16 字节），钥匙可以是 128/192/256 bit。DLMS 只用 128（Suite 0/1）和 256（Suite 2）。它本身只做“一块进、一块出”，不能直接处理任意长度的报文——那要靠“模式”。

输入16 字节明文块 + 16/32 字节密钥
输出16 字节密文块；同一块 + 同一钥匙永远得到同一结果

“同一块永远同一结果”既是优点（可预测、可用硬件加速），也是缺点：报文里重复的 00、重复的 OBIS 会在密文里暴露模式。所以需要 IV 和模式。

2.2 模式：ECB、CBC、CTR、GCM

模式怎么工作能否并行是否认证DLMS 用吗
ECB每块独立加密是否不用（会暴露模式）
CBC前一块密文异或进下一块加密不能，解密可以否不用
CTR加密“计数器块”，输出与明文异或是否作为 GCM 的加密内核
GCMCTR 加密 + GHASH 认证是是唯一使用

你不需要会实现 GHASH。你只需要记住 GCM 的“接口”：

GCM 加密 输入：K（EK）、IV（12 B）、P（明文）、A（AAD，可为空） 输出：C（与 P 等长）、T（tag，DLMS 固定 12 B） GCM 解密 输入：K、IV、C、A、T 输出：P，或者 FAIL（tag 不匹配）

2.4 三种保护组合：A 位与 E 位

SC 字节（Security Control）的 bit4 = A（认证），bit5 = E（加密），低 4 位 = 套件号，bit6 = Key_Set，bit7 = 压缩：

bit 5E 加密
bit 4A 认证

把任意一个 SC 字节输进去，它会拆成“套件 + A/E + 密钥选择 + 压缩”，并给出对应的 P/AAD/IV 规则。先用 0x30、0x21、0x32 各试一次。

§9.2.3.3.7.1 明说：仅加密时 tag “simply not computed and checked”。攻击者可以在密文里翻位，接收方照样解密，只是得到乱码——没有任何完整性保证。通用 GCM 库内部可能仍算出一个 tag，但协议不携带、不校验。

② 与 ③ 的密文完全一样：同一把 EK、同一个 IV、同一段明文。区别只在 ③ 多算了 tag，并把 SC‖AK 放进 AAD。这能帮你判断“密文对了但 tag 不对”时该查哪里。

解密时反过来做五步

① 读 SC：低 4 位定套件，A/E 定“有没有 tag、AAD 放什么”。② 读 IC：用发送方的 system title 拼 IV = Sys-T ‖ IC。③ 选钥匙：GUEK / GBEK / dedicated / ephemeral（general-ciphering 看 key-info）。④ 重建 AAD：仅认证是 SC‖AK‖明文APDU；认证+加密是 SC‖AK；仅加密为空。⑤ 验 tag 再解密：A=1 必须先验 tag，失败就丢弃；A=0 没有 tag，直接解密（也就没有完整性保证）。

2.6 GMAC：只贴封条

GMAC = GCM 在 P = 空 时的特例，只对 AAD 生成 tag。DLMS 用它做两件事：仅认证的报文保护；HLS mechanism 5 的挑战应答（T = GMAC(SC‖AK‖StoC)）。GMAC 仍然需要 IV，不是“不加密就不用 IV”。

2.7 AES Key Wrap：装钥匙的信封

要把新钥匙安全送到对面，需要一把“钥匙的钥匙”KEK。AES-KW（RFC 3394）就是专用信封：

  • 输入 KEK + 密钥（n 个 64-bit 块，n ≥ 2）；
  • 输出 n+1 个块，多 8 字节；多出来的是完整性校验；
  • 16 B 密钥 → 24 B；32 B 密钥 → 40 B；
  • 默认初始值 A6A6A6A6A6A6A6A6；用错 IV 会得到完全不同、且无法互操作的结果。

2.8 SHA-256 / SHA-384：指纹

哈希把任意长度输入压成固定长度输出，不可逆、难碰撞。DLMS 用它做 KDF、ECDSA 的预处理、HLS mechanism 6。它不是加密，也不能单独当 MAC 用（谁都能算）。

Chapter 3

非对称算法逐个讲：椭圆曲线、ECDH、ECDSA、证书

一句话直觉：对称钥匙的问题是“怎么把钥匙安全送到对面”。非对称用一对数学上绑定的钥匙解决：公钥可以公开，私钥只有自己有。ECDH 用它“隔着公开信道算出一把共同的钥匙”；ECDSA 用它“签个名，谁都能验但只有你能签”。

3.1 椭圆曲线：一张有限的“点加法”表

椭圆曲线在素数域上是一组满足 y² = x³ + ax + b (mod p) 的点。它有一个很好的性质：点可以相加，而且“已知 G 和 dG，求 d”极难（椭圆曲线离散对数问题，ECDLP）。

私钥 d一个随机整数（P-256 约 256 bit）
公钥 Q曲线上的点，Q = d × G（G 是公开的基点）

DLMS 只用两条 NIST 曲线（Table 21）：

套件曲线私钥公钥（未压缩）签名共享秘密 Z
Suite 1P-25632 B64 B（X‖Y）64 B（R‖S）32 B
Suite 2P-38448 B96 B（X‖Y）96 B（R‖S）48 B
公钥不是“一串随机数”，也不一定带 04 前缀

DLMS 在协商报文/Annex C 的示例里把公钥写成 FE2OS(x)‖FE2OS(y)，即裸的 X‖Y：P-256 = 64 B，P-384 = 96 B（Annex C 的表注明确写了这一点）。而 OpenSSL/SEC1 的“未压缩点”是 04‖X‖Y，会多 1 字节。直接把 OpenSSL 的输出塞进 key_data，长度就会是 65/97，对端按 64/96 解析必然错位。先把 04 去掉再拼。

3.2 ECDH：两个人各自算，得到同一个秘密

ECDH 的核心只有一行：

U 算：Z = d_U × Q_V V 算：Z = d_V × Q_U 因为 Q_U = d_U×G，Q_V = d_V×G， 所以 d_U×Q_V = d_U×d_V×G = d_V×Q_U。

攻击者能看到 Q_U、Q_V，但算不出 d_U×d_V×G——这就是 ECDLP。注意：ECDH 本身不认证对方。如果中间人替换了公钥，双方会各自和中间人算出不同的 Z。所以静态公钥必须通过证书或带外方式可信地获得。

3.4 ECDSA：签名，不是加密

ECDSA 用私钥对消息的哈希签名，输出一对整数 (r, s)。任何人都能用公钥验证，但只有私钥持有者能生成。DLMS 规定用 plain format：R‖S，各占 l = ⌈log₂n⌉ 字节，所以 P-256 签名固定 64 字节、P-384 固定 96 字节（§9.2.3.4.5）。

DER 与 plain 是两种格式，不能混

OpenSSL 默认输出 DER：30 45 02 21 00 … 02 20 …，长度可变。DLMS 要的是裸的 R‖S。把 DER 直接塞进 AARQ 的 AE-qualifier 或 HLS 的 f(x)，对端一定验不过。反过来，把 plain 当 DER 解析也会失败。收到签名先看长度：64/96 才是 DLMS 的 plain。

HLS mechanism 7 的签名输入是“两段 system title + 两个挑战值”，而且两个方向顺序相反（Table 50）：

客户端签（f(StoC)）：ECDSA( SysT-C ‖ SysT-S ‖ StoC ‖ CtoS ) 服务端签（f(CtoS)）：ECDSA( SysT-S ‖ SysT-C ‖ CtoS ‖ StoC )

注意是“先自己、后对方”，且挑战值也跟着换序。写反是最常见的“签名验不过”。完整的 Table 52 示例与验签代码见 第 7 章 7.7.1。

3.5 证书：把公钥和身份绑起来

裸公钥没有身份信息，中间人可以替换。X.509 v3 证书用 CA 的签名把“主体身份 + 公钥 + 用途”绑在一起。DLMS 用到的证书类型（Security setup 属性 6）：

certificate_entity（证书属于谁）certificate_type（证书干什么）
0 = server0 = digital signature（验签 / 不可否认）
1 = client1 = key agreement（ECDH 静态公钥）
2 = certification authority2 = TLS
3 = other3 = other

两个字段是独立组合，不是一一对应：一台表既可以有“server + digital signature”，也可以有“server + key agreement”。对接时先看 entity 再看 type，别把签名证书拿去协商。

3.6 一张 X.509 v3 证书里有什么

证书的本质是“CA 用私钥签了一段包含‘身份 + 公钥 + 用途’的数据”。结构只有三层：

Certificate ::= SEQUENCE {
  tbsCertificate       TBSCertificate,      -- 被签的内容
  signatureAlgorithm   AlgorithmIdentifier, -- CA 用的签名算法
  signatureValue       BIT STRING           -- CA 的签名（DER 的 ECDSA-Sig-Value）
}

TBSCertificate ::= SEQUENCE {
  version, serialNumber, signature, issuer, validity, subject,
  subjectPublicKeyInfo, extensions
}
字段DLMS 对接时看什么
issuer / subject谁签的、证书属于谁；DLMS 的命名方案见 §9.2.6.4.4
validity有效期；表计时间不准会导致“证书未生效/已过期”
subjectPublicKeyInfo曲线 OID（P-256 = 1.2.840.10045.3.1.7，P-384 = 1.3.132.0.34）+ 公钥点

subjectAltName可承载设备/系统标识；具体是否放 system title 由项目规范决定
basicConstraints是否 CA；终端实体证书通常 CA=FALSE
signatureValueCA 的签名，按 X.509 用 DER；不是 DLMS 报文的 plain R‖S
证书里的公钥点，和 DLMS key_data 里的公钥不是同一种包装

X.509 的 subjectPublicKeyInfo 里通常是 SEC1 未压缩点 04‖X‖Y（P-256 65 B，P-384 97 B）；而 DLMS 的 key_agreement.key_data 用裸 X‖Y（64/96 B）。从证书取公钥去拼 key_data 时，先判断要不要去掉 04。多一个字节，对端就按 64 B 切，后面全错位。

DER 与 PEM

DLMS 的 import_certificate 要 DER（二进制）。PEM 是 Base64 文本，带 -----BEGIN CERTIFICATE----- 头尾；导入前要去掉头尾、Base64 解码。把 PEM 原样塞进 octet-string 是最常见的“证书导入失败”。

4.3 三个常见误解

误解 1：Suite 0 = 不加密

错。Suite 0 的“认证加密”一栏就是 AES-GCM-128。它只是没有非对称算法。“不要求保护”是 security policy = 0 或 SC 的 A/E 都为 0，与套件号无关。Suite 0 + 强制加密是最常见的电表配置之一。

误解 2：套件号越高，报文一定越安全

套件只规定“可用算法”。如果 Suite 2 的连接用 LLS + 明文报文，安全性可能还不如 Suite 0 + HLS-GMAC + 认证加密。安全强度取决于实际启用的组合，不是编号。

误解 3：两端套件不同也能协商

不能。套件是配置，不是协商出来的。两端必须一致；不一致时通常表现为：AARQ 被拒、解密失败、tag 对不上，或者能建链但第一条受保护报文就崩。排查时先核对两端的 security_suite 属性。

  • 不可否认的计费/结算数据：服务端把关键读数签名后交给第三方，第三方事后不能否认收到过；客户端也不能伪造服务端的私钥签名。

  • 指令回执：对“已执行某条控制命令”的响应签名，便于事后追责。
  • 与加密叠加：需要同时保密和不可否认时，通常先签名、再加密（§9.2.7.3）；接收方先解密，再验签。第三方签名、客户端加密的分层场景也属于这一类。

Chapter 7

认证机制全集：8 种 mechanism（0–7）与 suite 的关系

一句话直觉：认证只回答“门开不开”，不回答“屋里说话要不要加密”。mechanism 0–7 共八个：0 不认证、1 报口令、2–7 是 HLS 的六种挑战应答。套件不决定“用哪个机制”，但决定“这个机制的算法能不能算出来”。

7.2 LLS：口令，明文，一趟

LLS 的流程只有一句话：客户端在 AARQ 的 calling-authentication-value 里放口令，服务端拿它和 Association 对象的 secret 比较。相符就建链，不符就拒绝。

LLS 的三个硬伤

① 口令明文走在 AARQ 里，AARQ 本身不受保护；② 只有单向认证，服务端不证明自己；③ 没有挑战，抓包可重放（虽然重放要先能建 TCP/链路）。所以 LLS 只适合“专网 + 物理受控 + 口令定期换”的场景。要改口令，用 Association 的 change_secret / change_HLS_secret 方法。

7.3 HLS：四趟，双向

HLS 的目标是双向认证：客户端证明自己，服务端也证明自己。做法是双方各出一个随机挑战，各自用共享秘密/密钥处理对方的挑战。

  • Pass 1：客户端在 AARQ 里放 CtoS（8–64 字节随机；mechanism 7 是 32–64）。
  • Pass 2：服务端在 AARE 里放 StoC。客户端必须检查 StoC ≠ CtoS，否则中止（§9.2.2.2.2.4）。
  • Pass 3：客户端调 Association 的 reply_to_HLS_authentication，参数是 f(StoC)。
  • Pass 4：服务端验证通过后，在方法响应里回 f(CtoS)；客户端验证。

可选的 system title / 证书：如果双方事先不知道对方的 system title，就在 calling-AP-title / responding-AP-title 里带；mechanism 7 还可以在 calling-AE-qualifier / responding-AE-qualifier 里带签名证书。已经知道就不必带。

7.4 八种 mechanism 逐个讲（0–7）

先回答“mechanism 与 suite 有关系吗”

规范里没有一张“mechanism × suite”的强制绑定表。mechanism 是 Association 的属性（建链时用哪个 OID 认证），suite 是 Security setup 的属性（报文保护能用哪些算法）。两者独立配置。

7.4.1 mechanism 0：No security（Lowest Level Security）

不是“认证”，是“不认证”。AARQ 不选认证功能单元，不带 mechanism-name、不带 calling-authentication-value；服务器按该 AA 的 access rights 直接放行。它只适合“读少量公共信息”或预建 AA。套件对它没有影响——因为根本没有密码学参与。

7.4.2 mechanism 1：LLS

AARQ 带 mechanism-name = 2.16.756.5.8.2.1 和 calling-authentication-value = 口令；服务器把它与 Association 对象的 secret 比较。单向、一趟、无挑战。口令明文走在 AARQ 里，而 AARQ 本身不受保护——这是 LLS 的硬伤。它和套件无关；套件只影响建链后的报文保护。

7.4.3 mechanism 2：HLS manufacturer specific

四趟流程与其它 HLS 一样，区别只在 f() 由厂商定义、方法保密。双方必须是同一厂商/同一套私有算法，否则无法互通。规范不规定它的 challenge 处理细节；挑战长度按 Table 50 是 8–64 B。

7.4.6 mechanism 5：HLS GMAC

f(StoC) = SC ‖ IC ‖ GMAC(SC ‖ AK ‖ StoC)   // 1+4+12 = 17 B

GMAC 是 GCM 在明文为空时的特例：P = 空，挑战值全部进 AAD。AK 是 Security setup 里的认证密钥；IV 用计算方本端的 Sys-T‖IC（规范未明写，Table 51 反推）。它的好处是 Suite 0 也能用，适合算力有限的表。

  • Suite 2：1 / 5 / 7。7 是“全套件强度”的干净选择；5 仍可用（AK 32 B）；机制 6 属兼容。
  • 老设备：3 / 4 只用于兼容，新设计不要选。
  • 专有生态：2；离开厂商就是黑盒。
机制与套件不匹配时，故障长什么样

① 服务器直接拒绝 AARQ（mechanism 不支持）；② AARQ 通过，但第 3 趟 f(StoC) 算不出来/对不上（算法不可用）；③ 两端都“支持”但强度不同（例如 Suite 2 用 mechanism 6），能通但不满足套件强度。排查时先看 AARQ 的 mechanism OID，再看 Security setup 的 suite，不要只看其中一边。

7.8 mechanism 与 suite 的关系（结论）

完整的 8×3 矩阵在 7.4.9，这里只留三句话：

  1. 没有规范强制的绑定表。mechanism 是 Association 的属性，suite 是 Security setup 的属性；规范只规定“套件里有哪些算法”，机制用到的算法必须落在其中。
  2. 0 / 1 / 2 与套件无关：No security、LLS、厂商自定义都不依赖套件的密码学；套件只影响建链后的报文保护。
  3. 5 三档都能用；6 是 Suite 1 原生；7 随套件选曲线：GMAC 用 AES-GCM（三档都有）；SHA-256 只在 Suite 1 的算法集里；ECDSA 在 Suite 1 用 P-256、Suite 2 用 P-384。Suite 0 没有 6/7 需要的哈希/ECDSA。

8.5 key_agreement：不传密钥，双方算出来

用 Security setup 的方法 3。请求参数是一个数组，每个元素：

key_agreement_data ::= structure {
  key_id   : enum (0 GUEK / 1 GBEK / 2 GAK / 3 KEK)
  key_data : octet-string        // Qe,U ‖ ECDSA(key_id ‖ Qe,U)
}
① 客户端生成临时密钥对 (d_U, Q_U)
② 签名用签名私钥签 key_id‖Q_U
③ 发送ACTION method 3，带 {key_id, Q_U‖sig}
④ 服务端验证签名 → 用自己的临时私钥算 Z
⑤ 派生KDF(Z, AlgID, Sys-TC, Sys-TS) → 密钥
⑥ 回应回 {key_id, Q_V‖sig}；双方密钥生效

为什么签名覆盖 key_id‖Q_U 而不是整个报文？因为它要防的是“把这次协商的公钥/密钥用途偷换掉”。签名绑定“这把公钥是给哪个 key_id 用的”，中间人不能把 GUEK 的协商结果挪去当 KEK。

协商出来的不是“最终密钥”，而是 KDF 的输入

ECDH 只给出 Z。最终密钥 = KDF(Z, AlgID, PartyU, PartyV)。AlgID 要区分用途：协商 GUEK/GAK 用 AES-GCM 的 OID，协商 KEK 用 AES-WRAP 的 OID。用错 AlgID，派生出的密钥“看起来也是 16 字节”，但两边对不上。

8.5.1 C(2e,0s) 的完整交互

请求参数的布局（P-256；key_data = 64 B 公钥 + 64 B 签名 = 128 B）：

C3 01 00 40 00 00 2B 00 00 FF 03 01 01 02 02 16 01 00 09 81 80 <Qe,U 64 B> <ECDSA(key_id‖Qe,U) 64 B>

09 81 80 是 A-XDR OCTET STRING 的长形式长度：0x81 表示“后面 1 个字节是长度”，0x80 = 128。P-384 时长度是 192，写成 09 81 C0。

from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.asymmetric.utils import decode_dss_signature

def build_key_data(signing_key, key_id, qe_raw, bits=256):
    """qe_raw = X‖Y（64/96 B），不是 04‖X‖Y。"""
    hash_alg = hashes.SHA256() if bits == 256 else hashes.SHA384()
    der = signing_key.sign(bytes([key_id]) + qe_raw, ec.ECDSA(hash_alg))
    r, s = decode_dss_signature(der)       # DER -> (r, s)
    n = bits // 8
    return qe_raw + r.to_bytes(n, "big") + s.to_bytes(n, "big")
签名是随机的，不要按“字节相等”去比对

ECDSA 每次签名用的随机数不同，同一把私钥、同一段消息，两次签出的 r,s 通常不一样。所以：验证签名要验签，不能拿两条签名做字节比较。对接测试时，看到两次 key_agreement 报文里的签名不同是正常的。

Chapter 10

自测 12 题与交叉验证记录

怎么用：先闭卷回答，再展开。答错的题回到对应章节，不要直接看答案——错误本身就是下一次排障的线索。
1. Suite 0 支持加密吗？它缺什么？

支持。Suite 0 的认证加密就是 AES-GCM-128，密钥传输是 AES-128 key wrap。它缺的是 ECDSA / ECDH / 哈希 / 压缩——所以不能在协议内协商密钥、不能做证书认证与数字签名。“不加密”是 policy=0 或 SC 的 E=0，不是 Suite 0 的定义。

2. 一条报文的 SC = 0x3A，怎么读？

0x3A = 0011 1010：低 4 位 1010 = 10（Suite 10，保留/未知）；bit4 A=1、bit5 E=1（认证+加密）；bit6 Key_Set=0（单播 GUEK）；bit7=0（无压缩）。Suite 10 不是合法值，说明对端用了保留套件或字节错位，先怀疑解析起点。

3. 为什么 GCM 的 IV 里要放 system title？

IV 必须在同一把钥匙下唯一。system title 标识设备（固定字段），IC 标识该设备的第几次调用（调用字段）。两者拼起来，保证不同设备、不同调用不会撞 IV。接收方用发送方的 ST + 报文里的 IC 重建 IV。

4. 仅认证和认证+加密，AAD 分别是什么？

仅认证：SC‖AK‖APDU（APDU 明文，必须整体纳入 AAD）。认证+加密：SC‖AK（APDU 已在 P 里，由 GCM 自动覆盖）。仅加密：空。

5. AES-KW 包装 32 字节密钥，输出多长？为什么？

40 字节。32 B = 4 个 64-bit 块，输出 n+1 = 5 个块 = 40 B；多出的 8 B 是完整性校验。与 KEK 是 128 还是 256 位无关。

6. KDF 的 PartyU/PartyV 顺序写反会怎样？

派生出的密钥完全不同。C.2 的两个方向：KDF(Z,AlgID,Sys-TC,Sys-TS) → 59A71FD8…；KDF(Z,AlgID,Sys-TS,Sys-TC) → F0184BDA…。顺序由报文里的 originator/recipient 角色决定。

7. LLS 和 HLS 的区别？HLS 为什么是四趟？

LLS 是客户端在 AARQ 里报口令，单向、明文。HLS 是双向挑战应答：① CtoS、② StoC、③ f(StoC)、④ f(CtoS)。四趟是因为两个方向各要出一道只有对方能算的题，互相验证。

8. HLS-GMAC 的 IV 用谁的？规范明写了吗？

用“计算这一趟的那一方”自己的 Sys-T‖IC：客户端算 f(StoC) 用客户端；服务端算 f(CtoS) 用服务端。规范 §9.2.7.4 没有明写 IV 构造；这是从 Table 51 两条向量反推并枚举验证的，对接需实测。

9. HLS mechanism 5 的 secret 存在哪个对象？

存在 Security setup 里，不在 Association 的 secret 属性里（蓝皮书 §4.4.4.2.7 注）。这是 GMAC 与 mechanism 3/4/6 的一个重要差别。

10. key_transfer 失败时，已经传成功的钥匙会生效吗？

不会。蓝皮书 §4.4.7.3.2：解包失败则方法失败，所有钥匙都不改变。实现要先全部解包校验，再一次性替换。

11. 为什么换密钥后 IC 要清零，而同一密钥下绝不能清零？

换密钥后旧 IV 空间作废，新密钥从 0 开始是安全的；同一密钥下清零会导致同一 IV 被用两次，GCM 会泄露明文异或关系，tag 也可能被伪造。

12. general-ciphering 的 401 字节，长度怎么加出来的？

1（DD）+ 9（transaction-id）+ 9（originator）+ 9（recipient）+ 1（date-time 空）+ 1（other-info 空）+ 1（key-info 存在）+ 1（agreed-key）+ 2（key-parameters）+ 130（Qe‖sig，含长度）+ 237（ciphered-content，含长度）= 401。

10.2 两处必须知道的“规范内部不一致”

① ECDSA 的两种编码：不是冲突，是两层

② HLS-GMAC 的 IV 与 IC 递增

生成顺序（用本工作区的 证书签发工具 或你自己的 CA）：

  1. Root-CA：选 Root-CA，CN 填 Root_CA，pathLen 填 1，有效期 10–20 年；生成后把 证书 PEM 和 CA 私钥 PEM 离线保存。CA 私钥不进电表。
  2. Sub-CA（可选）：角色选 Sub-CA，CN 以 CA 结尾，pathLen 填 0；用 Root 的证书和私钥签发。
  3. 服务端签名证书：生产环境不要用工具直接生成私钥；走 11.4 的 CSR 路径。实验室可用“终端证书 + 数字签名”，System Title 填电表的 8 字节 HEX。
  4. 客户端签名证书：同样方式，System Title 填客户端自己的 8 字节 HEX；私钥留在客户端软件/安全模块。
  5. 密钥协商证书：如果要用 C(1e,1s) 或 C(0e,2s)，再各生成一张 keyAgreement 证书；不要拿签名证书去协商。
  6. TLS 证书：只有 TLS 通道才生成；EKU 选 serverAuth/clientAuth，不要加 DLMS 签名用途。
  7. 验一遍：把生成的证书点“送到证书解析”，确认 CN、keyUsage、SKI/AKI、有效期与上表一致。
证书里的公钥包装

证书的 subjectPublicKeyInfo 里是未压缩点 04‖X‖Y（P-256 65 B，P-384 97 B）。把它拿去拼 DLMS 的 key_agreement.key_data 时，要去掉 04，只留裸 X‖Y（64/96 B）。多一个字节，后面全部错位。

11.4 电表内生成密钥：CSR 路径

这是生产环境唯一推荐的路径。原因很简单：DLMS 没有标准的“导入私钥”方法。Security setup 只有 generate_key_pair、generate_certificate_request、import_certificate；import_certificate 只收证书 DER，不收私钥。因此：

① 表内生成密钥generate_key_pair(0 签名 / 1 协商 / 2 TLS)
② 表内出 CSRgenerate_certificate_request(同类型) → PKCS#10 DER
③ CA 签发把 CSR 交给 CA；工具里选“签发 CSR”
④ 导入证书import_certificate(证书 DER)
⑤ 使用/更新更新时重新 ①–④；自己的证书不能只删不换

用工具签发 CSR 的步骤：

  1. 打开 证书签发，角色选“签发 CSR（电表内生成密钥）”。
  2. 把电表 generate_certificate_request 返回的 PKCS#10 贴进 CSR 框：支持 PEM、裸 Base64 和 DER HEX。电表返回 octet-string 时，直接切到 HEX 粘贴，不用先转 PEM。
  3. 签发者证书/私钥填 Root（或 Sub-CA）；留空则使用本次会话刚生成的 CA。
  4. 用途选“数字签名”（HLS-7）、“密钥协商”或“TLS”。
  5. 点“生成并签发”。工具只输出证书 PEM / DER HEX，私钥框为空——因为私钥一直在电表里。
  6. 把 DER HEX 或证书 DER 交给 import_certificate。
不要用“表外生成私钥再灌进去”

除非厂商明确提供密钥注入工具，否则不要把工具的私钥 PEM 写进电表。标准 import_certificate 没有私钥参数；私钥外灌会破坏“私钥不出设备”的安全边界，也会导致证书与表内密钥不匹配。

11.5 import_certificate 操作步骤

下面按“从一台空表开始”的顺序写。方法编号按蓝皮书 Security setup：4 generate_key_pair、5 generate_certificate_request、6 import_certificate、7 export_certificate、8 remove_certificate。

  1. 记录基线：读并保存 security_suite（属性 3）、security_policy（属性 2）、Association 的 security_setup_reference、当前认证方式和客户端权限。先备份配置，再动手。
  2. 确认初始通道：方法 6 通常要求已有安全会话或厂商模式。新表一般用 LLS/出厂口令/光学口做首次引导；如果表已经被策略锁死，先不要反复试，联系厂商恢复。
  3. 读证书数组：读 Security setup 属性 6 certificates，确认当前是空数组还是已有条目；同时读属性 3 确认 security_suite 是 1 或 2。
  4. 先导 Root-CA：用 import_certificate( Root_CA 的 DER )。Root 是信任锚，必须先于终端证书存在，否则后续验链没有落点。
  5. 再导服务端终端证书：import_certificate( 服务端签名证书 DER )。如果表支持 key agreement，再导服务端协商证书；TLS 需要时再导 TLS 证书。
  6. 导客户端证书：如果电表要在“没有收到客户端证书”的情况下也能验证客户端，把客户端签名证书也导进表里（entity=1）；否则可以只让客户端在 AARQ 里携带，电表用 Root 验。
  7. 核对条目：用 export_certificate(by_entity) 或 by_serial 把每张证书导出来，逐张核对 CN、keyUsage、AKI/SKI、有效期。不要只看“导入成功”就结束。
  8. 配置套件与策略：把 security_suite 设为 1 或 2；按需设置 security_policy 的认证/加密/签名位；把 Association 的认证机制设为 HLS-7。
  9. 最后才激活策略：security_activate 是单向棘轮，只能加强不能减弱。确认证书、密钥、客户端配置都正确后，再激活；激活后如果证书链有问题，远程可能已经登不上了。
  10. 做一次 HLS-7 会话：客户端在 AARQ 的 calling-AE-qualifier 带客户端签名证书；服务端在 AARE 的 responding-AE-qualifier 带服务端签名证书；双方各自用 Root 验链，再验挑战签名。
导入顺序与策略顺序

正确顺序是：Root → 终端证书 → 套件/机制 → 策略激活 → 测试。反过来先激活策略，再发现链缺一张，通常只能现场恢复。每次只改一层，改完立刻读回核对。

11.6 客户端与服务端配置

电表（服务端）
  • security_suite：1 或 2，与证书曲线一致
  • certificates：Root、服务端签名、服务端协商（可选）、TLS（可选）、客户端证书（可选）
  • Association：认证机制 7；security_setup_reference 指向 Security setup
  • 私钥：只在表内，由 generate_key_pair 产生
  • 策略：先测试，后激活
客户端
  • 信任锚：Root 证书（或直接钉住服务端证书）
  • 自己的签名证书 + 私钥；需要协商时再加 key agreement 证书 + 私钥
  • AARQ：calling-AE-qualifier 携带客户端证书
  • 验证 AARE：用 Root 验服务端证书，再验挑战签名
  • 时钟：证书有效期校验依赖本地时间

如果双方都只在 AARQ/AARE 里携带证书、且本地只有 Root，那么不需要把对方终端证书预置进来；如果现场为了减少报文长度或做 pinning，也可以预置对方证书，但要接受“换证就要同步更新”的运维成本。

11.7 验证与常见失败

每导入一张证书，至少做这五件事：

  1. 解析：确认版本 v3、CN 正确、有效期覆盖当前时间。
  2. 验链：终端证书 → Sub-CA（如果有）→ Root；每一级签名都验过。
  3. 查权限：CA 证书必须有 basicConstraints CA=TRUE 和 keyCertSign；终端证书的 keyUsage 必须与用途一致。
  4. 查绑定：终端证书的 CN（或 SAN 的 hwSerialNum）必须等于对端 System Title。
  5. 查曲线：Suite 2 用 P-384；Suite 1 用 P-256；混合链要确认签发者曲线与签名算法。

① GMAC 的 secret 是否从 Security setup 读（不是 Association 的 secret）；② IV 是否用了本端的 Sys-T‖IC；③ SHA-256/ECDSA 的输入顺序是否“先自己、后对方”，挑战值是否跟着换序。

期望：响应也是受保护的（按 policy + access rights 取更严者）；用服务端 system title + 响应里的 IC 重建 IV 解密。若 tag 失败，按“IV → 密钥 → AAD”顺序查，不要先怀疑算法。

A.6 第 4 步：换一把密钥

  1. 客户端生成新 GUEK（16/32 B，随套件）。
  2. 用当前 KEK 做 AES-KW，得到“密钥 + 8 B”的信封。
  3. 调 Security setup 的 key_transfer（方法 2），key_id = 0。
  4. 成功 → 新 GUEK 立即生效，IC 清零；失败 → 旧密钥不变，查 KEK/包装 IV。
  5. 用新密钥再发一条 GET，确认能通；不通就回退旧密钥或重传。
换密钥的顺序

先生成 → 再包装 → 再调用 → success 后才切换本地密钥。不要在发请求前就把本地旧密钥丢掉；否则服务端返回失败时，你连回退都做不了。

A.7 第 5 步：拆链与记录

发 RLRQ / 收 RLRE；如果 AA 使用 ciphering，user-information 里可能带一个受保护的 Initiate。拆链后记录：套件、策略、认证机制、system title、密钥版本、IC 当前值、最后一条报文的 tag 结果。

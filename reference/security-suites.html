安全套件速查：Suite 0 / 1 / 2

这张表要背下来的只有一件事：Suite 编号决定"哪些算法可用、密钥多长"；是否真的加密/认证，由 security policy 与 access rights 决定。 两者是正交的旋钮。

三套件的关系，一句话

Suite 0 只有对称密码（AES-GCM-128 + AES-128 key wrap），没有任何椭圆曲线算法；Suite 1 与 Suite 2 是同一个算法家族的两个强度档：128 位 / P-256 / SHA-256 对比 256 位 / P-384 / SHA-384。所以真正的分水岭在 0 与 1 之间，而不是 1 与 2 之间。

3在报文里怎么认出套件：Security Control 字节

套件号就写在每一个受保护报文的 security control byte（SC）的低 4 位。SC 后面紧跟 4 字节调用计数器 IC，两者合称 security header：SH = SC ‖ IC（§9.2.7.2.4.2）。

bit 7C 压缩
bit 6Key_Set
bit 5E 加密
bit 4A 认证
bit 3…0Security_Suite_Id

注意位序：A 在 bit 4、E 在 bit 5。把这两个记反，是排查"为什么对方拒绝我的报文"时最常见的自伤。

位含义（Table 45 逐字）：

  • bit 3…0：Security_Suite_Id —— 0 / 1 / 2，对应 Table 27；其余为保留值。
  • bit 4（A）：authentication applied —— 计算并携带 GCM tag。
  • bit 5（E）：encryption applied —— 明文被加密。
  • bit 6：Key_Set —— 0 = unicast（GUEK），1 = broadcast（GBEK）；使用 dedicated / general ciphering 时该位不适用，应为 0。
  • bit 7：compression 是否启用（V.44，仅 Suite 1 / 2 提供）。
动手

用 第 1 课的 SC 字节解码器 把 0x30、0x11、0x21、0x32、0x91 各点一遍，直到你不需要看表就能说出"套件 + 保护方式"。特别把 0x11 与 0x21 成对记：它们只差 bit5（E），一个是仅认证、一个是仅加密。

5四个最容易搞混的点

混淆 1

“Suite 0 = 不加密/无安全”是错的。Table 27 里 Suite 0 的认证加密一栏写的就是 AES-GCM-128：它照样能加密、能认证。它的真实短板是没有 ECDH/ECDSA/哈希，因此不能在协议内做密钥协商，也不能做数字签名与证书认证——密钥只能带外预置或用已有 KEK 包装。

混淆 2

“无保护”是另一个旋钮。security policy 取值 0 才表示 "no cryptographic protection is required"（Table 42 注）。套件与策略是两个独立维度：Suite 2 + policy 0 是完全合法的组合，只是浪费了能力。

混淆 3

“安全等级”不是规范里的字段名。绿皮书 §9.2 用 security policy（Table 42，逐位）与 access rights（Table 43，逐位）表达保护要求；各实现库（如 Gurux）用 Authentication / Encryption / AuthenticationEncryption 这种"安全等级"枚举对应 A/E 两位。看到别人说"这条用 level 3"，要问清是哪套术语。

混淆 4

保护强度取"更强者"。规范规定：应施加的保护取 security policy 与 access rights 两者中更强的要求（§9.2.2.4），并且 保护多于要求永远允许，少于要求一律拒绝（§9.2.7.2.2）。这解释了为什么改小 access rights 后原有客户端仍然能连通，反过来却会立刻被拒。

6套件配在哪里：Security setup 对象（实现视角）

规范层面的"算法组合"落到设备上，就是蓝皮书里的一个接口类：

  • “Security setup” 接口类，class_id = 64，version 1（蓝皮书 §4.4.7）。它的职责逐字是：“contain the necessary information on the security suite in use and the security policy applicable between a client and a server identified by their respective system title”。
  • 它由 Association 对象引用：Association LN 的 security_setup_reference 属性 / Association SN 的同名属性。也就是说——套件是"每条应用关联（AA）"的属性，不是全局属性。同一个服务端对不同客户端可以用不同套件。
  • 客户端与服务端由各自的 system title 标识，这也正是 IV 的固定字段（见第 2 节）。

version 1 还提供方法：security_activate、key_transfer、key_agreement、generate_key_pair、import_certificate、export_certificate、remove_certificate。其中一条规则值得现在就记住：

安全策略只能加强，不能削弱

蓝皮书 §4.4.7.3.1 逐字规定：“Once a kind of protection is added, it cannot be removed. If the method is invoked with a value indicating a security policy that is weaker than the value of the security_policy attribute, the method invocation fails.” 对实现者意味着：把安全策略调强是单向操作，回退需要客户端在带外被重新配置（而不是靠再调一次方法）。写自动化测试时要准备"先加强后无法撤销"的清理路径。

旧表的一个硬限制

如果设备上是 “Security setup” version 0（蓝皮书 §5.4.8，旧版本），它的 security_suite 取值范围逐字是 (0) AES-GCM-128 … (1) …(15) reserved——只能表达 Suite 0。这就是"我把配置改成 Suite 1 却怎么也生效不了"的常见根因之一：不是密钥不对，而是这个对象版本根本没有第二个值可填。此时需要的是固件里 version 1 的 Security setup。

配置侧与报文侧要能互相印证：配置里的 security_suite（属性 3）说明"允许用什么"，报文 SC 字节的低 4 位说明"这条实际用了什么"。两者矛盾时，先怀疑：读取的是不是另一条 AA 的 Security setup、或者读到的属性值被缓存了。

为什么要记住第二行

蓝皮书明确写着：“The same client may use different communication channels e.g. a remote port and a local port. The invocation counter on the different channels may be different.” 这解释了两件在现场很常见的事：① 同一个客户端走远程口和本地口的计数器可以各自独立，抓包对比时不要以为对方"计数器乱了"；② 计数器是要落盘的对象，重启后若从 0 重新开始，对端会按 §9.2.3.3.7.3 的规则拒绝（invocation-counter-error）。

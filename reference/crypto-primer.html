读懂套件表所需的密码学直觉

这份文档不是密码学教程，而是刚好够读懂 Table 27 的那一层直觉。卡住不要硬背：先读完每节的第一句话和"在 DLMS 里做什么"，其余跳过；用到再回来。

1AES-GCM：一个操作，同时给你"看不懂"和"改不了"

输入密钥 EK · 明文 P · 附加数据 AAD · 随机数 IV
→
AES-GCM计数器模式加密 + GHASH 认证
→
输出密文 + 96 bit 认证标签 tag

一句话直觉：AES-GCM 是"流式加密"和"校验和"的组合拳——加密让内容看不懂，标签让内容改不了；标签同时覆盖明文和 AAD，所以任何一处被改，验证就失败。

概念含义在 DLMS 里做什么
IV / nonce一次性随机数，同一密钥下绝不能重复8 字节 system title + 4 字节调用计数器 IC（§9.2.3.3.7.3）
AAD不加密、但参与完整性校验的数据承载 SC ‖ AK 等字段（Table 46）；认证密钥 AK 就是靠它参与保护的
tag96 bit 认证标签，附在报文尾部只有在 A 位为 1 时才计算并携带
密钥GCM 只有一个分组密钥DLMS 叫它加密密钥 EK；AK 不是 GCM 的密钥，而是进 AAD 的材料
最值得记住的一条

同一密钥下 IV 重复 = GCM 安全性崩塌。这就是为什么规范要为每个 EK 维护两个调用计数器（一个用于加密、一个用于解密），规定建立密钥时计数器归零、加密后自增 1、解密时校验"必须不小于最低可接受值"（§9.2.3.3.7.3）。你在代码里看到"计数器没存盘 / 重启后归零"，那是真问题，不是洁癖。

权威来源：NIST SP 800-38D（GCM 定义；绿皮书 §9.2.3.3.7.1 明确引用它）。入门读物：Crypto 101。

2AES key wrap：专门用来"包装密钥"的算法

一句话直觉：把一把密钥当作数据，用另一把密钥（KEK）把它裹起来，得到一个更长的密文；解开需要同一把 KEK。它比用 GCM 加密密钥更合适，因为它专为"被包装的东西本身就是密钥"设计，且带完整性保护。

  • DLMS 选用 RFC 3394 的 AES key wrap，按 64 bit 分块；n 个明文块 → (n+1) 个密文块（§9.2.3.3.8）。
  • 在 DLMS 里做什么：把新主密钥、全局密钥（GUEK/GBEK/GAK）从一端送到另一端；KEK 就是"主密钥"（§9.2.5.1 / Table 28）。
  • KEK 长度随套件：Suite 0/1 → 128 bit；Suite 2 → 256 bit。

3ECDH：双方各自算，算出同一个秘密

一句话直觉：双方各有一对密钥（私钥保密、公钥可公开）。把自己的私钥和对方的公钥一算，两边得到同一个共享秘密——而链路上只传过公钥，偷听者算不出来。这就是"密钥协商"。

DLMS 规定了三种方案（§9.2.3.4.6，绿皮书附录 C 有完整步骤），差别只在谁用临时密钥、谁用长期密钥：

方案规范记法直觉
Ephemeral Unified ModelC(2e, 0s, ECC CDH)双方都用临时密钥：前向保密最好，代价是每次都要新密钥对
One-Pass Diffie-HellmanC(1e, 1s, ECC CDH)一方临时、一方长期：一次往返就能协商
Static Unified ModelC(0e, 2s, ECC CDH)双方都用长期密钥：不需要额外往返，但没有前向保密

协商出的共享秘密不直接用，要先经过 KDF 派生（§9.2.3.4.6.5 采用 NIST 拼接 KDF）。规范另外规定：密钥派生一次只交付一把、用途单一的密钥，算法标识见 Table 26（§9.2.3.4.6.5 末）。

关键推论

Suite 0 的 Key agreement 一栏是 “–”：它没有 ECDH。所以 Suite 0 场景下密钥只能带外预置（出厂灌装、现场配置）或用已有 KEK 包装。这决定了整个系统的密钥运维方式——也是"很多表用 Suite 0"的真正原因。

4ECDSA：私钥签名，公钥验证

一句话直觉：用私钥对一段数据生成签名，任何人拿公钥都能验证"这确实是私钥持有者签的，且数据没被改"。与 ECDH 的区别：ECDH 用来协商出秘密，ECDSA 用来证明身份/数据来源。

  • 曲线随套件：Suite 1 → P-256；Suite 2 → P-384（Table 27）。
  • 在 DLMS 里做什么：高安全等级的 association 认证（证明客户端身份）、以及 digitally signed request/response（security policy / access rights 的 bit 4 与 bit 7）。
  • 公钥要可信，就得有证书：这就是蓝皮书的证书相关接口类与绿皮书 §9.2.6 存在的理由。

权威来源：FIPS 186-5（ECDSA）、NIST SP 800-56A（ECDH）。

5SHA-256 / SHA-384：哈希

一句话直觉：把任意长度的数据压成固定长度的"指纹"，改一个 bit 指纹就全变。它不保密，只用于摘要与派生。

  • Suite 0 没有规定哈希；Suite 1 → SHA-256；Suite 2 → SHA-384（Table 27）。
  • 用在哪：ECDSA 签名时的摘要、ECDH 共享秘密的 KDF（§9.2.3.4.6.5 规定每一步只派生一把用途单一的密钥，算法标识见 Table 26）。
一条别想当然

“从主密钥派生出加密密钥 EK 与认证密钥 AK”这种做法在实现里很常见，但绿皮书 §9.2 的这份文本并没有给出 EK/AK 的派生公式（本章只规定密钥的长度与用途）。如果你看到某个规范或代码声称在派生，先确认它依据的是哪一版、哪一节——这正是"读到引用再相信"的练习素材。
